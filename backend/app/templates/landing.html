membase

A research prototype exploring augmented personal memory, combining information retrieval, language models, and human-computer interaction.

It turns unstructured input into structured memory units, extracts the relationships between them, organises them into episodes, and retrieves by association and iteration rather than by matching alone — so a memory can be reached through what surrounds it, not only through what it says.

What it does

  • Capture of memory units

    One submission can describe several unrelated facts. The system splits it into independently retrievable units — you never have to do that split yourself.

  • Enforced authority hierarchy

    What you typed outranks what you later clarified, which outranks what the model inferred, which outranks the fully-derived search index. Nothing downstream ever overwrites something upstream of it.

  • Clarification gating

    A genuinely ambiguous term or date can hold a memory out of search until it's answered. It's bounded and skippable, and a real answer becomes part of the memory itself, not a transient chat message.

  • Attachments that are searchable all the way through

    PDFs, text and markdown are chunked — page-based or by fixed window — and every chunk is indexed independently, so a fact buried on page nine is findable rather than showing up as the first 500 characters of a document. Images are described by a multimodal model so they can be searched by what is visible in them.

  • Grounded retrieval, explicit abstention

    Search runs over the original text, its derived meaning, and chunked attachments. If the evidence doesn't support an answer, the system says so directly instead of guessing — the same code path as a real answer, not an error case.

  • Associative memory graph

    Memories are connected automatically through the people, places, organisations, concepts and visible objects they are about. Two notes that share no wording at all are one hop apart if they name the same lake, which is what lets recall reach a memory the query could never have matched directly. The graph is built from what extraction already produced, so it costs no additional model calls, and every edge records whether you stated the connection, a model extracted it, or the system merely computed it.

  • Associative, adaptive recall

    A clear query is answered directly. A vague one triggers graph exploration, evidence collection across candidates, and — only when it would actually help — one clarifying question chosen to maximise expected information gain rather than just asking for more detail.

  • Iterative recall

    Recall is a persisted, multi-round process rather than one request and one response. It accumulates what you are certain of, what you merely suspect, and what you can rule out, and asks one concrete discriminating question when several stored memories are still plausible instead of picking one arbitrarily.

  • Episodic memory

    Memories are grouped into the experiences they belong to — a trip, a semester, an evening — and browsable chronologically. Grouping is deterministic and needs no model call, including the titles. Dates and episode boundaries carry their own uncertainty: a memory with no recorded date is shown as undated rather than filed under the day it was typed.

  • Inspectable results

    Every substantial result can be unfolded into the memory it came from, the associations that led there, the evidence for and against it, the queries the system tried while searching, and which clarifications were incorporated. Confidence is a category — strong, moderate, weak, insufficient — never an invented percentage, because nothing here produces a calibrated probability.

  • Contradiction surfacing

    When two stored memories disagree, the disagreement is flagged for you rather than resolved automatically or hidden — and it caps how confident any answer drawn from them is allowed to be.

  • Background deepening

    Once a memory is searchable, a background pass keeps deepening its semantic representation over time without blocking anything on it. Corrections you make later re-derive only the layers beneath your own words.

How storage works

Writing a memory never edits anything after the fact. What you type is saved verbatim as a capture and never rewritten — everything else (search index, extracted meaning, later corrections) is layered on top of it, not in place of it.

A capture can become one or more memory units — one independently retrievable piece of memory each. A single note about two unrelated things becomes two units; one coherent story stays one.

Each unit carries a strict order of authority: what you typed outranks what you later clarified, which outranks what was automatically inferred, which outranks the fully-derived search index built from all of it. Nothing downstream ever overwrites something upstream of it.

A unit with a genuinely ambiguous term or date may hold one question before it becomes searchable — answer it, skip it, or discard that unit from the Library tab. Answering never changes your original words; it just adds to what the unit knows about itself.

The associative graph and the episodes built on top of all this are a deterministic, rebuildable projection of the stored memories, not primary data. They are derived from what extraction already produced, cost no additional model calls, and can be dropped and regenerated at any time. That is what makes a much richer representation of memory affordable without making the system depend on a fragile structure maintained separately from the memories themselves.

Deleting a capture (Library tab) is the only way a memory goes away — there's no automatic expiry or relevance-based forgetting.

Does any of it work?

The point of building this was to find out, so there is a benchmark rather than an assertion. Four retrieval strategies run read-only against the same 44 interconnected synthetic memories (57 retrievable units) and the same 40 queries, spanning exact, semantic, indirect-association, multi-hop, temporal, ambiguous, vague-episodic and deliberately unanswerable categories.

strategy recall@1 recall@5 correctness false retrieval ↓ LLM calls
conventional vector similarity 0.8290.8860.7710.401.95
hybrid search + LLM reranking 0.8000.8570.8570.603.27
associative (multi-hop) 0.8290.9430.8570.603.30
adaptive (iterative + clarification) 0.8570.8570.7140.806.75

Associative retrieval takes the best recall@5 — 0.943 against 0.886 for conventional vector search — without giving anything up elsewhere, for 0.03 more model calls. That is the result the whole design was aiming at.

Two things are reported here that a flattering write-up would omit. The margin is small: 0.943 against 0.886 is two queries out of 35 answerable, on a single run against a non-deterministic local model — a direction, not an established finding. And clarification made things worse: the adaptive strategy, which asks you a discriminating question, achieved the best recall@1 and the worst answer correctness — below plain vector search — with the worst false retrieval rate, at double the cost. Asking the user put the right memory on top more often and produced a worse answer from it. That is not what the design predicts, it is not yet explained, and it is recorded as an open question rather than quietly dropped.

False retrieval — how often a strategy answers a question the store genuinely cannot answer — is poor across the board and worst for the most capable strategy. This is why the Evaluation section deliberately computes no single combined score: the trade-offs are the result.

Inside the app

Every section below is open in the demo, reading the published snapshot of the synthetic store. Store is the exception: it exists only to write, so it asks you to sign in.

  • Store

    Write a memory, attach documents or images, answer a clarifying question if one is raised.

  • Recall

    Start from whatever you remember. Candidate memories with the evidence for and against each, matching passages from attached documents, the cues you have given, and the guesses the system made while searching.

  • Explorer

    The entity and association graph, with an inspector showing where each link came from.

  • Timeline

    Episodes in chronological order, with undated memories kept visibly undated.

  • Library

    Everything you've stored: review, correct, resolve clarifications, delete.

  • Evaluation

    The benchmark above, read from a published results file. The one section with no backend behind it — it's meant to be a readable report, not something behind a login.

  • Overview

    The state of your memory: what's stored, what's waiting on you, what's still processing.

Sign in

Signing in points the same app at a live backend and your own store: storing memories, answering clarifications, correcting and deleting them, and running new recall rounds against the model. Everything else is already open — browse the demo without one.

Self-service sign-up isn't available — credentials are provisioned by the project owner. Full architecture, design decisions, and the evaluation history: github.com/LuxKaiwalker/membase.
